The FFmpeg Codebase

A guided tour of the libraries, the pipeline, the core structs, codec internals and where to start reading.

The one-sentence version

FFmpeg is not really one program. It is a family of C libraries that implement a media pipeline, plus a few small command-line programs — ffmpeg, ffprobe and ffplay — that wire those libraries together.

file / URL / camera
      |
      v  libavformat     demux: identify the container, split out streams
   AVPacket              compressed bytes
      |
      v  libavcodec      decode
   AVFrame               raw pixels / raw samples
      |
      v  libavfilter     scale, crop, overlay, volume, subtitles
   AVFrame
      |
      v  libavcodec      encode
   AVPacket
      |
      v  libavformat     mux: write MP4 / MKV / TS
   output file

The usual early confusion: demuxing is not decoding, and encoding is not muxing. A demuxer pulls compressed packets out of a container; a decoder turns packets into raw frames. The encoder and muxer do the reverse.

Repository layout

DirectoryWhat lives there
libavutil/Foundation: AVFrame, AVBufferRef, AVRational, formats, math, logging
libavcodec/Biggest directory. Decoders and encoders: h264dec.c, hevc/, libx264.c, libx265.c, bitstream readers, SIMD in x86/
libavformat/Demuxers, muxers and protocols: mov.c, movenc.c, matroskadec.c, mpegts.c, http.c
libavfilter/Filter graph engine plus filters: vf_scale.c, vf_crop.c, af_volume.c
libswscale/Pixel-format conversion and resizing: sws_scale()
libswresample/Audio conversion: swr_convert(), sample rate, channel layout
libavdevice/Capture/output backends: x11grab.c, v4l2.c, pulse.c
fftools/The CLI programs: ffmpeg.c, ffprobe.c, ffplay.c, plus split-out demux/decode/filter/encode/mux files
configureCustom configure script; generates config.h and config.mak
ffbuild/Make fragments used by the build
doc/examples/Small complete example programs — the best entry point
tests/FATE regression suite

The types you must know

TypeMeaning
AVFormatContextOne open input or output. Holds streams, duration, metadata, I/O context
AVStreamOne track inside the file: codec id, size, sample rate, time_base
AVCodecContextLive codec state: negotiated dimensions, pixel format, quality, private options
AVPacketCompressed chunk: data, size, pts, dts, stream_index
AVFrameDecoded raw data: video planes or audio samples, plus pts and format

Two supporting ideas matter more than they look:

  • AVRational time_base: timestamps are integers interpreted in a per-stream fraction such as {1, 90000}. Many A/V sync bugs are timebase bugs.
  • AVBufferRef: reference-counted memory. Packets and frames rarely copy pixels; they pass refs around. Mutating a frame you do not own is a classic mistake.

Read the pipeline in code

The skeleton of doc/examples/demux_decode.c looks like this:

avformat_open_input(&fmt, "in.mkv", NULL, NULL);
avformat_find_stream_info(fmt, NULL);

for (each stream) {
    const AVCodec *dec = avcodec_find_decoder(par->codec_id);
    avcodec_alloc_context3(dec);
    avcodec_parameters_to_context(dec_ctx, par);
    avcodec_open2(dec_ctx, dec, NULL);
}

while (av_read_frame(fmt, &pkt) >= 0) {
    avcodec_send_packet(dec_ctx, &pkt);
    while (avcodec_receive_frame(dec_ctx, frame) == 0) {
        /* AVFrame: raw pixels/samples -- filters, then encoder */
    }
}

Modern FFmpeg uses the send/receive API. Old tutorials that call avcodec_decode_video2() describe an API removed years ago.

How one codec is implemented

Take H.264 as an example:

  • AVCodec is a struct of function pointers: init, decode, close, flush, and capability flags.
  • AVCodecContext->priv_data points to a codec-specific struct holding SPS/PPS, slice state and reference frames.
  • Bitstreams are read with get_bits.h helpers such as get_bits() and show_bits(), not byte-by-byte string logic.
  • Shared H.264/H.265 syntax lives in h2645_parse.c; H.265 has its own libavcodec/hevc/ directory.
  • Hot loops have hand-written SIMD in libavcodec/x86/ and arm/ — hence the _sse2, _avx2, _neon variants chosen at runtime.
  • Third-party encoders are wrappers: libx264.c, libx265.c, libvpxenc.c, libaomenc.c. They exist only if configure found the external library.

That last point explains the VLC codec problem from earlier. Fedora's ffmpeg-free was configured with --disable-decoder='h264,hevc,vc1,vvc', so CONFIG_HEVC_DECODER was zero and those AVCodec entries were never compiled in. VLC's libavcodec_plugin.so had no decoder for avcodec_find_decoder() to find. Installing the RPM Fusion build flipped those flags on.

The build system

./configure probes the compiler and libraries, then generates config.h, config.mak and ffbuild/config.mak. Source files are full of guards such as #if CONFIG_HEVC_DECODER, and Makefiles pull in objects conditionally. That is why flags like --enable-gpl, --enable-libx265 and --enable-cuda change the resulting binary.

Tests are FATE: reference clips plus expected hashes, described in tests/fate/*.mak and run with make fate.

Best reading order

  1. doc/examples/demux_decode.c and doc/examples/transcode.c: small, complete, no CLI noise.
  2. libavformat/demux.c: where av_read_frame() lives now.
  3. libavcodec/decode.c and encode.c: send/receive machinery and threading.
  4. libavfilter/graphparser.c: how a string such as scale=1280:-1,eq=gamma=1.1 becomes a graph of filter nodes.
  5. Only then fftools/ffmpeg.c, which is the full conductor and is harder to read cold, especially after the recent split into ffmpeg_demux.c, ffmpeg_enc.c and ffmpeg_mux.c.

For exploration without reading C: ffprobe -show_streams file.mkv, ffmpeg -decoders, ffmpeg -h encoder=libx265, ffmpeg -filters and ffmpeg -loglevel debug are all useful.

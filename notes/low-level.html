A Practical Path into Low-Level Programming

Pointers, compilers, C, memory allocators — and a capstone that connects all of it to FFmpeg and SDL3.

Stage 0 — Toolchain

sudo dnf install gcc make gdb strace ffmpeg-devel

ffmpeg-devel supplies the headers needed to compile against the libraries already installed. Compile every exercise like this:

gcc -std=c11 -Wall -Wextra -Wpedantic -g \
    -fsanitize=address,undefined -o test test.c

AddressSanitizer catches use-after-free, buffer overflows, double frees and leaks at runtime. It replaces most of what valgrind is used for; valgrind is not installed here, but gcc's sanitizers are.

Stage 1 — Pointers and C itself

The mental model that makes everything click:

  • All memory is bytes with addresses. A pointer is an address plus a type that tells the compiler how many bytes to read or write.
  • An array is not a separate entity: a[i] is *(a+i). Arrays decay to pointers when passed to functions.
  • A C string is a char array ending in a zero byte (NUL). There is no string type.
  • sizeof(p) is the size of the pointer (8), not the pointee. Use sizeof(*p) for the latter.
  • void * is a generic address; C converts it to and from any object pointer implicitly (unlike C++).

Exercises, in order

  1. swap(int *a, int *b) and print addresses with printf("%p", (void*)p).
  2. Reimplement strlen, strcpy, strcat, strcmp without using libc string functions.
  3. A dynamic array: struct Vec { void *data; size_t len, cap; } with vec_push() built on realloc().
  4. A singly linked list with a list_free() that leaks nothing (verify with ASan).

Draw boxes and arrows on paper for exercises 3 and 4. It is faster than staring at the code.

Recommended first book: C Programming: A Modern Approach by Kenneth N. King. Alternative: K&R chapters 1–5 if you like terse classics.

Stage 2 — What a compiler actually does

Run each command on a tiny hello.c and inspect the output:

CommandWhat it shows
gcc -E hello.cPreprocessed source: macros and includes expanded
gcc -S hello.cGenerated assembly
gcc -c a.c -o a.oObject file: machine code plus symbol table
nm a.oSymbols defined and referenced
objdump -d a.oDisassembly
readelf -h a.oELF headers
ar rcs libmine.a a.o b.oStatic library
gcc -v ...Full pipeline: cpp → cc1 → as → ld

Then split pilot.c into pilot.c and pilot.h, add include guards, and deliberately cause an undefined reference error and a multiple definition error. Learning to read those two messages saves hours later.

Use godbolt.org to compare -O0 and -O2 side by side. That is where pointers stop being abstract: a[i] becomes a base register plus an offset.

This is also the answer to "how does FFmpeg work": libavcodec.so is a pile of object files exporting symbols such as avcodec_find_decoder. VLC links against it and calls those symbols. No magic.

Stage 3 — Memory model and allocators

high addresses
 +----------------+
 | stack          |  grows down: locals, return addresses
 +----------------+
 | (gap)          |
 +----------------+
 | heap           |  grows up: malloc / free / realloc
 +----------------+
 | .data / .bss   |  globals, static variables
 +----------------+
 | .text          |  machine code, read-only
 +----------------+
low addresses

See your own version with cat /proc/self/maps.

Key facts

  • malloc() asks the OS for pages (mmap/brk) and carves them into chunks. It is not itself a syscall.
  • Alignment: allocations are padded to 8 or 16 bytes. (p + 15) & ~15 rounds a pointer up to 16.
  • Padding: struct { char c; int x; } is 8 bytes, not 5. Field order matters.
  • realloc() may move your data; old pointers into that block become dangling.
  • Refcounting is how FFmpeg avoids copying frames: AVFrame->buf[] holds AVBufferRefs.

Allocator exercises

  1. Bump allocator: static char arena[65536], a bump_alloc() that advances an offset with alignment. No free.
  2. Free-list allocator: a small header before each block (size, next), implement my_free(), then coalesce adjacent free blocks.
  3. Refcounted buffer: struct Buf { void *data; size_t size; int *refs; } with buf_ref() and buf_unref() — a miniature AVBufferRef.
  4. Write buggy versions on purpose and watch ASan catch them.

For the "why": Computer Systems: A Programmer's Perspective (CSAPP), chapters 2, 3, 5 and 6.

Stage 4 — The Linux systems layer

Learn these calls and their man pages: open/read/write/close, mmap, fork/exec/wait, pipe, pthread_create, mutexes and atomics. Trace them with strace -e trace=file ./app.

Exercises: a 20-line cat; a cp implemented with mmap; a fork() plus pipe() pair; and a shared counter with and without a mutex so you can see the race.

Book: Advanced Programming in the UNIX Environment (APUE).

Stage 5 — Capstone: your own mini-ffplay

  1. After installing ffmpeg-devel, find the header location: rpm -ql ffmpeg-devel | grep avcodec.h.
  2. Compile doc/examples/demux_decode.c from the FFmpeg source against those headers.
  3. Instead of writing raw frames to a file, feed them into your pilot.c SDL3 texture.
  4. Now you have demux → decode → scale → render: ffplay in miniature.
  5. Bonus: route frame buffers through your own arena/refcount allocator.

Do not wait until you have "finished" all of this before touching FFmpeg. Do stages 1–3, then read doc/examples/demux_decode.c alongside stage 4. Keep one small program you own and add one layer at a time — which is exactly what Pixels in C already is.
